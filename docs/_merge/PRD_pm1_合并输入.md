## 1. 唯一的实质分歧：目标分数 83.0 vs 84.0

### 1.1 先说结论：我们算的是两个不同的东西

| 版本 | 数字 | 实际回答的问题 | 推理路径 |
|---|---|---|---|
| 你的 83.0 | 能力预测 | 「**我们大概能做到多少**」 | bottom-up：83.2 − 数据折损 − 配方折损 + 后处理增益 |
| 我的 84.0 | 竞争门槛 | 「**进 TOP3 需要多少**」 | top-down：83.2（TOP3 至少得够到论文水位）+ 1.0 确定增量 − 0.2 安全垫 |

**两个数字都对，而且都应该留在 PRD 里**——它们之间的差值（1.0–2.0pp）恰好是这份 PRD 要管理的核心对象：**需要靠工程执行去挣的溢价**。

**建议方案：拆成两个命名数字，写进 §1.1。**

| 名称 | 值 | 用途 |
|---|---|---|
| **能力预测**（bottom-up） | **80–84，中位 ~82** | 规划用：决定要不要做集成、要不要做分辨率实验等投入项 |
| **竞争门槛**（top-down） | **82–85，目标取 84.0** | 驱动用：目标是用来决定"要不要花 300 元""要不要做集成"的 |
| **执行缺口** | **1.5–2.0pp** | PRD 的核心管理对象 |

### 1.2 为什么目标要按门槛定、而不是按能力定（这是我坚持 84.0 的理由）

1. **目标会自我实现**。若按能力定 82，就会自然地砍掉所有高投入项（集成、分辨率实验、付费算力），然后真的停在 82。**目标的作用是拉伸执行，不是描述现状。**
2. **你的 §1.2 第 9 步有个逻辑漏洞**：你估的门槛区间是 82–84，却取了 83.0（区间中部）。若真实门槛是 84（强队多的情景），定 83.0 就等于**预先接受了失败**。目标应取门槛区间的**上沿 + 安全垫**。
3. **你的 §1.2 第 8 步说强队 82–85**。若第 3 名落在 84，我们需要 > 84，不是 83。

### 1.3 我对你的推理链提一个质疑：第 6 步「零训练成本增益 +1.5~3.5pp」存在重复计算

**问题**：83.2 是 α-SimADNet **完整管线**的论文报告值。完整管线必然已包含：B 样条/折线输出、置信度阈值标定、NMS、去重、坐标裁剪。论文不可能拿未后处理的原始输出去报 SOTA。

逐项核对你的附录 B：

| 附录 B 项 | 是否已 baked in 83.2 | 是否为真增量 |
|---|---|---|
| B 样条稠密化输出 | **是**（否则无法与 GT 折线算 IoU） | 否 |
| 置信度阈值验证集标定 | **是**（必然已标定） | 否（除非做**场景自适应**阈值，那是真增量） |
| 线长过滤 + 横向 NMS 去重 | 大概率是 | 存疑 |
| TTA | 论文通常不做 | **是** |
| 场景条件化 CLAHE | 论文未做 | **是** |
| 本地 metric 复刻 / 打包校验 / 台账 / 沙盘 | — | 间接项，不应计入 F1 增益 |

**修正后**：能力预测 = 78.7~81.7（你的第 5 步，复现水位）+ **真增量 1~3pp**（TTA / 场景 CLAHE / 场景自适应阈值 / 分辨率） = **79.7~84.7，中位 ~82.2**。

> 修正量只有 ~0.5pp（你的中位 82.7 → 82.2），**结论方向不变**。但构成变了，这很重要：**我们真正的增量来源是"论文没做的事"，不是"把论文做过的事重做一遍"**。这会改变精力分配——应该优先做场景条件化、TTA、分辨率，而不是把通用后处理再打磨一遍。

### 1.4 需要配套的降级条款（你的 R16 已有此意，建议提到正文 §1.1）

## 2. 你遗漏的一个决策点：输入分辨率（我认为这是本赛题最易被忽视的天花板）

### 2.1 论证

| # | 论据 | 类型 |
|---|---|---|
| 1 | 10px 容差定义在 **1366×720 原图坐标系**上 | 【事实】 |
| 2 | CLRNet 系常规输入 800×320 → 宽度缩放 **0.586**、高度缩放 **0.444** | 【事实】框架默认 |
| 3 | 模型在 800 宽输入上偏差 1 像素 → 映射回原图 = **1.71px**。输入分辨率直接决定定位精度的**量化步长** | 【测算】 |
| 4 | 高度压到 320 → 纵向采样步长 = 720/320 = **2.25px/行**；CLRNet 类方法的 row-anchor 设计下，端点纵向定位误差会被系统放大 | 【测算】 |
| 5 | **这可能是「F1@0.7 断崖式下跌」的部分原因**——不是模型不够好，而是坐标系压缩把精度锁死了。F1@0.7 对应 d = 5.3px，在 800 宽坐标系下只有 3.1px，已接近量化步长量级 | 【推测】 |

### 2.2 建议的需求条目（可插入你的域 C，编号 P1-C29）

| 编号 | 需求描述 | 验收标准 |
|---|---|---|
| **P1-C29** | 输入分辨率 A/B：至少对比「框架默认 800×320」与「高分辨率档（建议 1366×720 或等比 1024×540）」 | ① 各跑 **15 epochs 短跑**；② 高分辨率档在验证集 F1 提升 **CI 下界 > +1.0pp** 才采纳；③ 采纳后核算单 epoch 耗时增幅并更新算力台账；④ 输出坐标必须映射回 **1366×720 原图坐标系** |

### 2.3 建议的执行优先级（并入你的 §4.7 决策点表）

1. **零训练成本后处理**（你的 P0-C10）— 0 GPU 小时，最先做
2. **输入分辨率 A/B**（P1-C29）— 1 次短跑
3. **场景条件化 CLAHE**（你的 P1-C17）— 1 次短跑
4. **TTA**（你的 P1-A16）— 推理期，几乎零训练成本
5. **第二架构 / 集成**（你的 P1-C21）— 最后才考虑

理由：**分辨率是"天花板型"因素，不是"增益型"因素**。如果它对，其他所有优化的收益才能兑现；如果它错，后面全在错误的坐标系里调参。所以它的优先级应高于 CLAHE，但低于零成本后处理。

## 4. 对你两处数字的建议修正

### 4.1 「4090 ≈ T4×2 的 3 倍」偏乐观，建议按 2.0× 保守排期

| 项 | 数值 |
|---|---|
| 4090 vs T4 单卡：FP16 张核算力 ~165 vs 65 TFLOPS | 2.5× |
| 4090 vs T4 单卡：显存带宽 1008 vs 320 GB/s | 3.1× |
| → 4090 ≈ T4 单卡综合 | **3~4×** |
| T4×2 DataParallel 有效加速（TASKS.md 取值） | 1.7× |
| → **4090 ≈ T4×2 的** | **1.8~2.4×，取 2.0× 保守** |

**影响**（你的 §4.1 / 附录 A）：

| 项 | 你的估计（3×） | 建议值（2.0×） |
|---|---|---|
| 4090 单 epoch | 12–15 min | **~23 min** |
| 36 epochs 完整训练 | 7.2–9h | **~13.6h** |
| 172 元（68.8h）可做完整训练次数 | 5.8 次 | **~5 次** |

**不改变结论**（混合方案 C、300 元预算仍成立），但要改一处措辞：你写的「**一个晚上能看到一次完整训练结果**」在 2.0× 下不成立（13.6h 接近一天）。建议改为「**约一天一次完整训练**」，否则会误导排期预期。
（此项对应你的 Q9，建议把 Q9 从"确认速率"升级为"9/3 前必须实测，作为全部排期的基准"）

### 4.2 「P50 ≤ 5px」是必要条件而非充分条件

你的半正态推导（σ=7.3 → P50=4.9px、P(X<10)=82.9%）数学上完全正确，我验算过。

但**半正态假设对长尾不敏感**：真实误差分布是**重尾**的（弯道、十字路口、重度反光的误差会远大于 σ）。重尾下，同样的 P50=5px 会对应**更低**的 P(X<10px)。

**建议**：P0-C11 的两个指标都保留，但明确 **P(X<10px) ≥ 83%（即 P83 ≤ 10px）是绑定指标，P50 ≤ 5px 仅作快速诊断用**。理由：全集汇总 + 等权重意味着长尾决定成败，而 P50 对长尾不敏感。
